# FlowBoard Engineering Standards

**Status:** approved baseline, derived from the TAS-7 plan (§5) accepted by Anas on 3 October 2026 (decisions CL-D1, CL-D9 and CL-D10 in `CLARIFICATIONS.md`).
**Applies to:** every change in this repository, by any agent or person.
**Companion documents:** `ARCHITECTURE.md`, `CLARIFICATIONS.md`, `adr/`, `specs/README.md`.

Citations use **FS §n** for `docs/product/FUNCTIONAL_SPEC.md`, **BM §n** for `docs/product/BUSINESS_MODEL.md` and **CL-xx** for entries in `CLARIFICATIONS.md`. A rule without a citation is an engineering choice made to keep a three-person team productive (FS §10) and to limit key-person risk (BM §10).

---

## 1. Coding standards

### 1.1 TypeScript strict everywhere

- All three packages (`flowboard-api`, `flowboard-web`, `flowboard-shared`) compile under `"strict": true` from a shared `tsconfig.base.json`. `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` are on.
- `any` is forbidden unless a comment on the same line explains why no narrower type exists. `unknown` plus a Zod parse is the default at every boundary (HTTP, WebSocket, database rows, environment).
- ESLint and Prettier run in CI and fail the build on any error or formatting difference. Do not disable a rule in code without a comment naming the reason.
- Node.js 22 LTS, pnpm workspaces. The package manager version is pinned in the root `package.json` `packageManager` field.

### 1.2 Shared contracts in `flowboard-shared`

- Every request body, query string, response, WebSocket event and activity event type is a Zod schema in `flowboard-shared`. The API validates with the schema; the web app imports the inferred TypeScript types. Nothing is typed twice (FS §7 requires broadcast events and stored activity events to be identical, so one schema serves both).
- The FS §5.2 activity event names are a single `const` enum in `flowboard-shared`. Adding an event type means adding it there first.
- OpenAPI is generated from the Zod schemas, never hand-written.
- Breaking API changes require a new versioned path. FS §7 fixes the public surface at `/v1`; `/v1` routes never change shape once merged. Additive, optional fields are allowed.

### 1.3 Database changes through migrations only

- Schema changes are SQL migrations generated by Drizzle and committed to git. No manual changes to any database, including local ones, that are not reproduced by a migration. Every migration has a tested down path.
- Every table has `id` (UUID v7), `created_at` and `updated_at`.
- Soft delete is an `archived_at` timestamp (nullable) on `board`, `list` and `card`. Application code never issues a physical `DELETE` on those tables (B-06, C-13, L-06, CL-A2). Physical removal happens only in the scheduled purge job after the retention constant (CL-A6).
- `activity_event` is insert-only. No update or delete statements against it anywhere in application code (FS §5.2 "append-only and never edited"). A database role without `UPDATE`/`DELETE` on that table enforces it in production.
- Ordering columns (`list.position`, `card.position`, `checklist_item.position`) are sparse floats (FS §5.1). Position maths lives in one module in `flowboard-shared` with unit tests, including the re-balance routine.

### 1.4 Authorisation is server-side and matrix-tested

- The FS §6 permission matrix (Workspace admin, Board admin, Board member, Observer) is enforced in the API on every route by a single authorisation module. Route handlers call it; they never embed role checks inline.
- Every route has an integration test per role, positive and negative, generated from the matrix. A new route that is not in the matrix test fails CI.
- The UI hides what the user cannot do (FS §6) but never relies on hiding. A forbidden action returns `403` from the API regardless of the client.
- Server rules take precedence over the prototype where they differ (CL-E1: card member picker offers board members only).

### 1.5 No secrets in git

- No credentials, tokens, keys or connection strings are committed, including in tests, fixtures, Docker Compose files or CI workflows. `.gitignore` excludes `.env` and `.env.*` except `.env.example`.
- `.env.example` documents every environment variable with a description and a safe placeholder. The API refuses to start when a required variable is missing and says which one.
- Agents receive secrets through Paperclip secret proposals and grants, never through issue comments or files. Local development uses the Docker Compose Postgres with a throwaway password that is itself documented as non-secret.
- Pull requests that add a file matching a secret pattern fail CI (secret scanning).

### 1.6 Externalised strings and accessible presentation

- Every user-visible string in `flowboard-web` lives in a message catalogue, never inline in a component (FS §8 internationalisation). No translations are produced in MVP (CL-E7), but the catalogue is the only place text appears.
- CSS uses logical properties (`margin-inline-start`, not `margin-left`) so the layout is RTL-ready (FS §8).
- Colour is never the only carrier of meaning (FS §8). Due-date badges, WIP pills, label chips and status indicators all carry text or an icon as well.
- Dates are rendered in the user's locale and timezone with `Intl` APIs; the API stores and transmits UTC ISO 8601.
- Every interactive element is keyboard-reachable with a visible focus ring. Every drag action has a menu equivalent (C-11, FS §8). Modals trap focus and restore it on close (FS §8).

### 1.7 Conventional Commits and small pull requests

- Commit messages follow Conventional Commits: `type(scope): summary`, with types `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`, `perf`. Scope is the package or backlog ID (for example `feat(api): FB-04 board hydration`).
- Every commit made by an agent ends with the co-author trailer required by the working agreement.
- A pull request addresses one backlog item or one correction. If a change needs more than roughly 400 changed lines of hand-written code, split it.
- Pull request descriptions link the Paperclip issue, list the FS story IDs covered, and include the verification evidence required by §2.

### 1.8 One owner, one branch, one worktree per task

- Every implementation task has exactly one owner agent. Backend and frontend work for the same backlog item are separate tasks with separate owners when both are needed.
- Each task works on its own branch named `<type>/<backlog-id>-<slug>` (for example `feat/FB-04-boards`) in its own git worktree. Two agents never write to the same checkout. Worktrees live under `.worktrees/` (git-ignored) or in the agent's Paperclip workspace.
- Branches are short-lived and trunk-based: branch from `main`, rebase on `main` before review, merge by squash or rebase after approval. No long-running integration branches.

### 1.9 Independent review

- Every pull request is reviewed by an agent who did not write it. FlowBoard Lead never sole-reviews its own work.
- Review is a Paperclip task delegated to the reviewer with a self-contained description; the verdict is posted on that task. The authoring task is blocked on the review task until the verdict lands.
- A reviewer checks the §2 definition of done item by item and names any unmet item. "Looks good" without the checklist is not a review.

### 1.10 Human merge approval

- Anas gives human acceptance and merge approval before any merge into `main`. Agents open pull requests and attach evidence; they do not merge.
- Production deployment is authorised separately from merge approval.

### 1.11 Pushing and opening pull requests from an agent run

- Agents push and open pull requests through `tools/paperclip-git.cjs`, which obtains the run's managed GitHub credentials from the Paperclip broker and starts the real `git.exe`. Paperclip's own managed launcher does not start on Windows (Paperclip issue TAS-35), so plain `git push` prompts for credentials and fails.
- Push: `node tools/paperclip-git.cjs push -u origin <branch>`. Open a pull request: `node tools/paperclip-git.cjs pr create --title "<title>" --body-file <file> --head <branch>` (base defaults to `main`). Write the description to a file first so quoting is not an issue.
- Local commits, worktrees and reads do not need the wrapper. The wrapper never prints the credential; do not copy the token out of it or paste it anywhere.
- Until this tool is on `main`, run it from the branch that carries it: `git show origin/chore/FB-00-windows-git-launcher:tools/paperclip-git.cjs > "$env:PAPERCLIP_SCRATCH_DIR\paperclip-git.cjs"` and call that copy with `node`.

### 1.12 Scratch branches, red-run proofs and merge safety

Decided by FlowBoard Lead on 4 October 2026 (Paperclip issue TAS-60) after the scratch branch `scratch/TAS-49-red-proof` was merged into `main` through pull request #26, whose title said "DO NOT MERGE", and broke `main` until the revert in pull request #27. Every agent pushes and opens pull requests under the repository owner's GitHub account (§1.11), so a pull request's author and title are the only signals a merger sees; nothing in the repository enforced them.

- **A red-run proof never opens a pull request.** When an acceptance criterion requires proving that a CI gate fails closed, push a `scratch/<backlog-id>-<slug>` branch, let the `push` trigger in `.github/workflows/ci.yml` run it, and cite the branch's Actions run URL as the evidence. Delete the branch once the evidence is cited. There is nothing to merge, so there is nothing to merge by mistake.
- **`scratch/**` is never a pull request head.** Scratch branches hold experiments and proofs only. Work intended for `main` lives on a `<type>/<backlog-id>-<slug>` branch (§1.8).
- **The `Merge guard` job fails on scratch work.** CI runs a lightweight job on every pull request that fails when the head branch matches `scratch/**` or the title contains `DO NOT MERGE`, `SCRATCH` or `WIP`. The job exists so that a scratch pull request opened by mistake shows a red check instead of relying on the merger reading the title.
- **Required status checks on `main` are the real control.** Anas approved a GitHub ruleset on `main` on 4 October 2026 (**CL-D11** in `CLARIFICATIONS.md`, superseding the open assumption CL-O9): the checks `Lint`, `Typecheck`, `Unit tests`, `Integration tests`, `Build`, `Playwright smoke` and `Merge guard` must pass before a pull request can merge, with no bypass actors, and force-pushes to and deletion of `main` are blocked. Repository rulesets are a repository setting, so Anas applies it; CL-D11 lists the exact settings. Until the ruleset is live, the guard job and the no-pull-request convention above are the only protection, and a red check is advisory.
- **Renaming a CI job changes a required check.** The job `name:` values in `.github/workflows/ci.yml` are what the ruleset matches. A pull request that renames one of the seven required jobs must say so in its description so Anas updates the ruleset in the same step; otherwise every later pull request waits on a check that never reports.
- A GitHub "required approving review" rule is **not** recommended: with a single GitHub identity for Anas and every agent, no one could approve a pull request they are deemed to have authored. Independent review stays in Paperclip (§1.9) and merge approval stays with Anas (§1.10).

## 2. Definition of done

A task is complete only when all nine items hold. Partial completion is reported as partial, with the unmet items named.

| # | Requirement | Evidence expected on the Paperclip task |
|---|---|---|
| 1 | **Acceptance criteria demonstrated.** Every acceptance criterion in the task maps to FS story IDs (or BM sections) and each is demonstrated. | Checklist in the pull request description with the story ID next to each criterion. |
| 2 | **Unit tests for domain logic.** Position maths, filter logic, due-date buckets, permission matrix and any other pure logic have unit tests (Vitest). | Test file paths and the passing run output. |
| 3 | **Integration tests against real Postgres.** Every new or changed API route has integration tests (Fastify inject against Docker Postgres), including authorisation failures for every role. | Passing run output; new routes appear in the matrix test. |
| 4 | **End-to-end test per story, accessibility check per screen.** A Playwright test exists for each user story touched, named with the story ID. axe-core runs on every new or changed screen and reports no violations. | Test names and the passing run; axe report. |
| 5 | **Browser verification evidence.** Any UI change attaches screenshots or a Playwright trace showing the behaviour in a real browser. | Attachment on the Paperclip task. |
| 6 | **CI green.** Lint, typecheck, unit, integration, build and the end-to-end smoke subset pass on the pull request head. | Link to the CI run. |
| 7 | **Independent review.** Reviewed by an agent who did not write the change (§1.9). | Link to the review task and its verdict. |
| 8 | **Documentation updated.** Specification in `docs/engineering/specs/`, an ADR if a decision was made, `CLARIFICATIONS.md` if an answer was recorded, `ARCHITECTURE.md` if the system shape changed. | Files in the pull request diff. |
| 9 | **Human acceptance and merge approval.** Anas has accepted the work and approved the merge. Deployment is a separate authorisation. | Anas's approval on the Paperclip task or pull request. |

Never claim a test passed without the run output. Report unverified behaviour explicitly.

These run on CI independently of any single task once the relevant backlog item lands.

|---|---|---|

## 4. Testing conventions

- **Unit (Vitest):** colocated as `*.test.ts` next to the module. Pure functions only; no database, no network.
- **Integration (Vitest + Fastify inject + Docker Postgres):** under `flowboard-api/test/`. Each file truncates the tables it touches. Fixtures come from the shared seed that recreates the three prototype boards (FB-01).
- **End to end (Playwright):** under `flowboard-web/e2e/`, one file per backlog item, tests named `<STORY-ID> <behaviour>` (for example `B-02 creates a board with three default lists`). Runs against the real API and database, never mocks.
- **Accessibility:** `@axe-core/playwright` assertion in every end-to-end test that renders a new screen.
- **Performance:** Playwright trace on the seeded 1,000-card board with a CPU and network throttle, asserted against the budget in §3.
- Tests that are skipped must say why in a comment and link a Paperclip issue.

## 5. Repository conventions

- Layout per `ARCHITECTURE.md` §6. Management inputs under `docs/product/` are read-only for engineering.
- `README.md` at the root must take a fresh clone to a running API and web app in under 15 minutes (FB-00 acceptance). Any change that breaks that path is a bug.
- Local development runs with one command and a Docker Compose Postgres. No cloud dependency until hosting is approved (CL-D8).
- `.editorconfig` at the root; LF line endings; UTF-8 without BOM.
- Specifications follow `specs/README.md`. No implementation task starts without a specification approved by Anas for scope and acceptance criteria.

---

## 6. Working with Paperclip

- Engineering specifications, standards and ADRs live in git. Assignments, dependencies, progress, review verdicts and evidence live on Paperclip issues.
- Every implementation task carries: one owner, scope, requirement references (FS/BM/CL IDs), acceptance criteria, dependencies (`blockedByIssueIds`) and the verification expected from §2.
- Updates on a task state what is complete, what evidence exists, what is blocked and who owns the next action.
- Credentials never appear in task comments or documents.
