# FlowBoard Clarifications Log

**Purpose:** the dated record of every clarification, decision and recorded answer that engineering relies on but that the management inputs do not state (or state inconsistently). Specifications and tasks cite entries here by ID (for example **CL-D3** or **CL-A2**) instead of re-deriving the answer.

**Rule:** the management inputs in `docs/product/` are never edited. When a decision changes the reading of a requirement, the change is recorded here and the input stays as written.

**Sources cited:** `docs/product/FUNCTIONAL_SPEC.md` (**FS §n**, story IDs such as **B-02**), `docs/product/BUSINESS_MODEL.md` (**BM §n**), `docs/product/flowboard-prototype.html` (**PT**). The analysis that produced these decisions is the TAS-7 plan document (Paperclip issue TAS-7, document `plan`); its conflict table is cited as **TAS-7 §2.n**.

**Status values**

| Status | Meaning |
|---|---|
| **Approved** | Decided by Anas (Product Owner). Binding for implementation. |
| **Recorded** | Engineering reading accepted by Anas without objection. Binding unless Anas revises it. |
| **Open** | Engineering assumption not yet put to Anas. Implementation may proceed on the assumption, and the task that depends on it must say so. |

| **CL-E44** | `activity_event_card_created_idx` carries `id`, and the page is cut before the actor join | CL-E38 ("`activity_event_card_created_idx` already serves the query"); FB-06 §7 ("if the activity query plan on a card with 1,000 events shows the index unused, the backend task adds `id` to it in a new migration and records the query here"); FS §8 | The measurement FB-06 §7 asks for shows the FB-01 index **not** serving the feed: ordered `(created_at desc, id desc)` it is a bitmap scan plus a top-N sort over the card's whole history. ### 3.6 Engineering decisions recorded during implementation (10 October 2026, FB-07 backend re-balance, TAS-141)

These are readings the inline re-balance needed that FB-07 does not fix: one about lock ordering inside the move transaction, one about how acceptance criterion 8 can be satisfied at all. Both are engineering choices inside approved scope (CL-E36, CL-E41, CL-E45), recorded in the same pull request per the CL-E22 precedent.

| ID | Topic | Resolves | Decision | Consequence | Spec |
|---|---|---|---|---|---|
| **CL-E49** | The container lock is taken before the move is written, and both lists are locked on a cross-list move | CL-E36 ("holding the list row with `SELECT … FOR UPDATE`"); FB-07 §6 ("after writing the position, lock the destination container"); FS §5.1 | FB-07 §6 describes the re-balance as running after the position is written, and it still does. The `FOR UPDATE` on the container row, however, is acquired **before** the card or list row is updated. Taking it after would let a mover hold the card row while waiting for the list, at the same time as a concurrent re-balance of that list holds the list while waiting for the card — a lock cycle Postgres resolves by aborting one move with a deadlock error the client never asked for. A cross-list card move locks the source **and** the destination list, in ascending id order, so two movers swapping cards between the same pair of lists also take the two locks in the same order. Only the destination is re-balanced; the source lock exists purely for the ordering. The container of a card is its list; the container of a list is its board. | `lockLists` in `repositories/card.ts` and the board `SELECT … FOR UPDATE` in `updateList`. No semantic change to CL-E36: the same rows are rewritten with the same positions and the same absence of activity events. `updateList` becomes transactional, which it was not in FB-05 (it was a single statement). | FB-07 |
| **CL-E50** | AC 8's "midpoint between the same two neighbours" is the gap above a fixed neighbour | FB-07 AC 8 ("60 consecutive `PATCH` moves that each place a third card at the midpoint between the same two neighbours … exactly 60 `card.moved` events"); CL-E45 | Read literally as `positionBetween(left, right)`, the criterion is self-contradicting: after the first drop the card already sits at that midpoint, so by CL-E45 the next 59 `PATCH`es change nothing and write no event, and the run yields one `card.moved` rather than 60. The two re-balance tests therefore send `positionBetween(left.position, mover.position)` — the card is dropped into the shrinking gap immediately above the same `left` neighbour every time. That is the construction that halves a gap on each drop and so exercises the precision exhaustion CL-E36 exists for, and it produces exactly the 60 events AC 8 requires. Relatedly, "after the run the list's positions are evenly spaced" is asserted at the moment a re-balance fires rather than after the 60th drop: a drop that does not cross the threshold leaves the card at a midpoint by definition, so the container is only evenly spaced immediately after a rewrite. The end state is asserted on what does hold throughout — relative order preserved and `needsRebalance` false. | `test/cards.move.rebalance.test.ts` and `test/lists.move.rebalance.test.ts`, both with the reading in the file header. No production behaviour depends on it. | FB-07 |

## 5. How to add an entry

1. Choose the next ID in the right section (D for an Anas decision, A for a recorded answer, E for an engineering reading approved as part of a plan, O for an open assumption).
2. Cite the FS, BM or PT location that the entry clarifies and, where one exists, the TAS-7 conflict row.
3. State the consequence for the data model, API or UI in one line so a reader does not have to infer it.
4. Add the date to the section heading when a new batch of decisions lands. Do not edit earlier entries; add a superseding entry and mark the old one "Superseded by CL-xx".
5. Never edit `docs/product/`.
